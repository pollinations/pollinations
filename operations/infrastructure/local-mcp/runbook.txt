LOCAL MCP PILOT: RUNBOOK

Unpublished, single-operator pilot of local-shell-mcp (fwerkor/local-shell-mcp
066abd563016bf20aee5df9e9a752b5ba8d9e396, MIT) as a remote-only relay:

  cloud agent -> https://local-mcp.pollinations.ai/mcp (OAuth) -> named
  Cloudflare tunnel -> controller container on community-monitor
  (3.221.108.127, arm64) <- outbound worker <- Thomas's Mac

Not in the Gen registry or app catalog. Nothing here is live until every
gate below is passed, each with its own approval.

FILES

  Dockerfile, requirements-controller.in/.txt   controller image: pinned base
      digest, upstream archive checked by SHA-256, complete hashed lock.
      Regenerate the lock with the command at the top of the .txt.
  compose.yaml, cloudflared.yaml   controller (uid 10001, read-only, 512 MiB,
      0.50 CPU, loopback port 18765) and tunnel sidecar (128 MiB, 0.25 CPU,
      outbound only). No inbound EC2 port, no Docker socket mount. Only
      the project network's fixed subnet (10.254.75.0/28; verify.sh uses
      10.254.76.0/28) may set X-Forwarded-For, so PIN retry limits and the
      audit log key on the client address Cloudflare appended.
  preflight.py, verify.sh   local shell/files/stdio registration denied,
      only the compose subnet may set the client address, OAuth metadata,
      401 for missing/invalid bearer. Public fixtures only.
  local-mcp-pilot   root-owned SSH forced command on the host. It runs
      the host's standalone Docker Compose v5.6.1 at
      /home/ubuntu/pollinations-local-mcp-pilot/bin/docker-compose (the host
      has no Compose plugin) after checking its SHA-256; CI uses the same
      binary.
  ci-remote.sh, known_hosts   the Actions side; host and host key pinned.
  bootstrap-host.sh   installs or updates the deploy identity.
  local-mcp.test.cjs, test-bootstrap.sh   command restrictions and switch,
      restore and stop logic; bootstrap as root on a throwaway CI runner.
  .github/workflows/deploy-local-mcp-pilot.yml   Deploy / Local MCP pilot.

HOW A DEPLOY WORKS

  Thomas dispatches the workflow on production (operation: deploy) and
  approves the local-mcp-pilot-production environment. CI builds and checks
  the image on an arm64 runner, then SSHes as local-mcp-deploy with
  "deploy <production SHA>". The host wrapper confirms the SHA is on
  production (GitHub compare API), downloads only the fixed release files at
  that SHA, builds and runs verify.sh; a failure there leaves the live
  release alone. It then switches and checks limits, loopback OAuth/401 and
  the same through https://local-mcp.pollinations.ai. Only then is the
  release live. If any check fails it restores the release that was live
  and checks it the same way; if there was none (first activation) or the
  restore fails, it stops the pilot and checks the public URL is down.
  rollback uses the same switch; stop and status skip the build.

  The host rebuilds from the same reviewed files, hashed lock, pinned base
  digest and checksummed upstream archive as CI. It does not reuse the CI
  image, so the two are not byte-identical; each is verified separately.

WHAT THE DEPLOY IDENTITY CAN AND CANNOT DO

  Can: status, stop, rollback, and deploy any commit reachable from
  production. Cannot: shell, PTY, port/agent/X11 forwarding, sftp/scp,
  Docker socket, other projects (authorized_keys "restrict" + forced
  command; sudoers allows only the wrapper with no arguments).
  Not claimed: the wrapper runs as root and Compose is root-equivalent, so
  anyone who can merge to production decides what runs on the host. A
  holder of the deploy key can redeploy or stop the pilot. The controller
  holds the JWT key and PIN in its environment; host and Docker admins can
  read them and all relayed command/file data. The public check proves the
  route serves an OAuth-protected controller naming the pilot issuer, not
  which release answers; the loopback check ties that to the release.

OPERATIONS

  Deploy, status, stop and rollback run only as Actions dispatches on
  production; there is no admin-SSH path for them. stop removes only this
  project's containers and checks the public URL no longer answers; state
  volume, secrets and releases stay, and the last live release becomes the
  rollback target. With no previous release, rollback refuses; use stop.
  status succeeds for a stopped or never-deployed pilot and fails when the
  recorded release has no running controller or fails a check.
  Stopping the Mac's foreground worker (Ctrl-C) is the immediate cutoff
  for the Mac and needs neither Actions nor the host.

  Rolling back the activation: dispatch stop, then remove the
  local-mcp.pollinations.ai DNS route added in gate 3c. Removing that new
  route is not a secret mutation and needs no separate secret approval.

LIFECYCLE LIMITS

  The deploy key, JWT signing key, admin PIN and tunnel credential do not
  expire. Access tokens last one hour; there is no per-token revoke, and a
  new PIN does not invalidate issued tokens. Rotating or revoking any
  credential, and deleting the tunnel, deploy authorization, GitHub secret
  or secret files, each need a new scoped secret approval. Deleting the
  state volume (pollinations-local-mcp-pilot_state) needs Thomas's
  approval: registry backups in it contain worker credentials.
